# PHP+MySQL 课程设计/上机任务

这类任务分两种完全不同的形态，**开工前先判断是哪一种**，因为后续流程分叉很大：

- **形态A：迁移开发大作业**——老师给 DEMO 网站 + 数据素材 + 任务书，要做一个新业务领域的完整网站 + 设计说明书。走下面 1~7 节。
- **形态B：上机操作考试**——任务书本身就是一张"考卷"，按大题小题给分点，每完成一步要截图，**直接贴回这份 docx 试卷**对应题目下方的空白处，不需要另外写说明书。走本文末尾"形态B：上机操作考试"那一节。

判断依据：任务书里如果出现"得分""评卷人""截图得X分"这种表格化的按点给分描述，且没有提供 DEMO 网站，那就是形态B；如果是"选题＋功能模块清单＋提供 DEMO 文件夹"这种，就是形态A。

这类任务的本质（形态A尤其如此）：**老师给的 DEMO 不是要抄的答案，是要拆解的教学样本**。它演示了"会话鉴权 + mysqli 增删改查 + 分页 + 批量操作"这一整套模式，学生要做的是把这套模式套到一个新的业务对象上（图书 → 学生 / 录取信息 / 借阅 / 训练营学员 / 其他任何自选主题），同时补上 DEMO 里偷懒或过时的地方。**每一个新项目的业务对象、字段、模块划分、报告内容都必须重新从"这次的 DEMO + 这次的数据 + 这次的任务书"推导出来** —— 别把上一次做过的某个具体项目（表名、字段名、模块名、报告措辞）原样搬过来，那是抄自己的作业，不是复用方法论。真正可以照搬的是下面这套**流程和踩过的坑**，以及 `scripts/`、`references/` 里那些跟业务无关的工具代码。

## 形态A整体流程

1. 吃透三份材料 → 2. 设计新的数据模型和模块清单 → 3. 迁移代码（不是照抄，是升级） → 4. 本地真实跑通 → 5. UI 值得认真做 → 6. 按模板写说明书 → 7. 打包，检查提交要求

下面按顺序展开，每一步都写了"为什么"和"上次踩的坑"。

## 1. 吃透三份材料

任务书 docx、DEMO 网站、数据素材（xls/xlsx 或现成的 .sql），三者缺一不可，开工前必须都读一遍，因为：DEMO 决定了"怎么实现"，任务书决定了"做够几个模块、每个模块具体要求什么"，数据素材决定了"数据库该长什么样"。

- **任务书/说明书模板是 docx，但环境里大概率没有 Word、没有 LibreOffice、没有 pandoc。** 别因为读不了就跳过或瞎猜内容。用 `unzip` 把 docx 解开是 zip 包，`word/document.xml` 里用正则把 `<w:t>...</w:t>` 之间的文本拼出来就能拿到全部正文，包括封面字段、目录结构、任务清单。具体做法见 `references/extracting_docx_without_office.md`。**尤其要留意封面模板里那些"看起来像示例"的字段**——上次就吃过亏：模板封面里的学院名、指导教师名字其实是学校给这门课批量填好的真实信息（旁边配了真实校徽图片），只有专业班级/学号/姓名这几个明显带"___"或"***"的才是真正要学生自己填的空。**用 `qlmanage -t -s 1600 -o 输出目录 文件.docx`（macOS 自带 QuickLook）能不装 Word 就把 docx 首页渲染成图片看一眼**，比纯读文本更容易分清"真占位符"和"已经填好的真实值"。
- **通读 DEMO 的每一个文件**，搞清楚它的业务对象（表名、字段）、鉴权方式（通常是 session 判断 + 每个受保护页面顶部重复一段检查代码）、增删改查各是怎么拼 SQL 的、分页怎么做的、批量删除的复选框怎么提交的。这决定了新系统"应该长成什么样子"——任务书要求的功能点，DEMO 里几乎都能找到对应实现可以参考。
- **数据素材如果是老版 `.xls`（不是 `.xlsx`）**，`openpyxl` 打不开，要用 `xlrd`（`pip3 install xlrd==1.2.0`，新版 xlrd 已经砍掉了 xls 支持，必须指定 1.2.0）。读出来的字段名和示例数据，直接决定了新数据库表的列设计。

## 2. 设计新的数据模型和模块清单

把任务书里"要求实现的功能点"列成一张表，逐条对应到具体模块，数量必须明显超过任务书写的最低要求（比如"不少于5个"就做到 8~11 个），且**登录、增、删、改、查每一类都至少要有一个**——这是任务书评分的硬指标，做的时候心里要一直有这张对照表，报告里也要放这张表证明"任务书要求的都做到了"。

常见可以自然扩展出的模块（DEMO 一般只给了最基础的那几个）：条件删除 vs 列表选中删除 vs 批量/全选删除是三个不同模块；条件修改 vs 列表选中修改是两个模块；再加一个统计分析模块（按某个维度 GROUP BY 统计人数/均值/最值），既好实现又能凑数量还确实有用。

数据库设计上，主键选数据里天然唯一的那一列（学号/考生号/编号之类），字段名可以用拼音缩写（照抄 DEMO 的英文命名风格，比如 `bookid/bookname` 那种"字段拼音首字母"命名法在这类课程作业里是常态，不必纠结改成更"专业"的英文命名）。

## 3. 迁移代码：升级，不是照抄

复用 DEMO 的**结构**（页面怎么分工、导航怎么摆、鉴权怎么做、分页怎么写），但下面几点要主动做得比 DEMO 好，这也是报告里"设计思路"部分最好写的加分项：

- **DEMO 里的 SQL 基本是字符串拼接 `$_POST['x']` 直接塞进 SQL 语句，这是教学演示里的坏习惯，照抄就是把 SQL 注入漏洞也一起搬过来了。** 全部改成 `mysqli_prepare` + `mysqli_stmt_bind_param` 的参数化查询，这个改动量不大但是报告里可以专门写一节，是真实的技术亮点，不是凑字数。
- **`conn.php` 里一定要加 `mysqli_report(MYSQLI_REPORT_OFF);`**（放在 `mysqli_connect` 之前）。原因：PHP 8.1+ 的 `mysqli` 默认在出错时抛异常而不是返回 `false`，而所有照着 DEMO 风格写的 `if($result){...}else{...}` 判断都假设"失败会返回 false"。不加这行，本地用新版 PHP 测试时，随便一个主键冲突就是一屏致命错误堆栈（还会把服务器文件路径暴露出去），而不是你精心设计的"添加失败"提示。这个坑几乎每次用新版 PHP 本地测试 DEMO 类代码都会踩到，提前加上就不会踩。
- **把重复的页头/导航/页脚/鉴权抽成 `common/` 下的公共文件**（`auth.php`、`header.php`、`footer.php`），每个功能页面开头 `include` 一下。DEMO 里每个页面都整段复制了导航栏 HTML，这是它最大的"技术债"，抽出来之后新增模块、改版式都只用改一处，报告里也可以写一句"降低了维护成本"。
- **不要把 DEMO 自带的图片资源（顶部横幅、logo）原样搬过来。** 这类模板图片上通常直接印着 DEMO 自己那个业务的名字（比如"某某书屋图书借阅管理系统"），换了业务对象还用这张图，页面标题和横幅文字对不上，一眼能看出是没认真改的抄袭痕迹。要么用纯 CSS 做新横幅（写一行系统名字 + 渐变背景，比找图/画图快得多），要么自己配一套跟新业务相关的配色。

## 4. 本地真实跑通，别只是"看起来能跑"

**不要在用户已有的 MySQL 实例上直接建库测试**——那是用户机器上其他项目在用的数据库服务，贸然连接、建库、改 root 密码都有风险。正确做法是起一个完全隔离的临时 MySQL：独立数据目录、独立端口、独立 socket，测试完直接整个删掉，不留痕迹。`scripts/setup_isolated_mysql.sh` 已经封装好这一套（`mysqld --initialize-insecure` 建空实例 + 指定 socket/port 启动），传一个工作目录和端口号就能用。PHP 用不了就用 Homebrew 装（`brew install php`），配合 PHP 内置服务器 `php -S 127.0.0.1:端口` 起站点，不需要完整装一套 Apache。

测试要覆盖**每一个模块的正常路径和异常路径**（不存在的主键查询、重复主键添加、必填项为空、条件删除找不到记录……），而不是登录进去点一圈觉得像样就完事。两个实操细节：

- **前端有 `confirm()` 二次确认弹窗的操作（删除类），浏览器自动化工具点了按钮但对话框不一定能正确处理，会显得"没反应"。** 这时候直接绕过前端，用 `curl -b cookie.txt -d "字段=值" 目标.php` 模拟表单提交去验证后端逻辑对不对，前端确认框只是 UX，不影响这样测。
- **测试环境的 PHP 版本（本机装的多半是新版）和最终部署环境（老师给的老版 WampServer，往往是 PHP 5.6）可能有行为差异**，第 3 节提到的 `mysqli_report` 就是活生生的例子。写完代码顺手 grep 一下有没有用 PHP 7+ 才有的语法（`??`、箭头函数 `fn()`、`<=>` 之类），确保老版本 PHP 也能跑。

## 5. UI 值得认真做，"能用"和"像样"是两回事

DEMO 的界面通常是 2010 年代画风的裸 `<table>` 布局，直接照抄的话哪怕功能全对，视觉上一眼就能看出是没花心思的作业。**别只是加个配色就交差**——如果用户说"丑""再优化"，说明第一版的改动量不够，需要的是换一套布局范式（比如从"顶部横向导航的老式页面"换成"侧边栏导航的后台管理系统"风格），而不是调调颜色、加个圆角。值得做的事：统一的侧边栏/顶栏导航组件、自绘几个简单的内联 SVG 图标（不依赖外部图标库，方便离线用）、首页放几张关键指标的统计卡片、表格加斑马纹和悬停高亮。这些改动量不大，但视觉观感的提升是数量级的。

做完之后**真的登录进去，把每个模块点一遍**（用浏览器工具截图确认，不要只是"代码写完了应该没问题"）。

## 6. 按给定模板写设计说明书

任务书里通常写明"设计说明书按提供的模板来写，占大头的分数"（这次是 60%），说明报告的完成度和源代码同等重要，不能潦草对待。

- 先用第 1 节的方法把模板 docx 的结构（封面字段、目录层级）抠出来，说明书要**逐节对应**模板目录，不能自己另起一套结构。
- 生成 docx 本身：环境里大概率没预装 Node 的 `docx` 库，`npm install docx` 装到一个临时工作目录就行，不需要全局装。`references/docx_report_toolkit.js` 是一套现成的排版辅助函数（中文标题字体、代码块、图表、封面表格、自动目录域），**这套工具函数可以整段复用**，但每次调用它生成的具体内容——摘要怎么写、每节讲什么、代码贴哪几段、模块怎么分——必须重新为这个项目写，不能把上一个项目的说明书内容改几个词就交差，那样报告里会出现对不上号的表名字段名。
- **报告里的运行截图必须是真实跑起来的系统**，不能拿设计稿凑数。用登录接口先拿到一个真实的 session cookie（`curl -c cookie.txt -d "..." .../checkuser.php`），再用这个 cookie 把每个页面的 HTML 连同 CSS 一起存到本地，最后用 headless Chrome（`--headless --screenshot=out.png --window-size=宽,高 file:///本地页面.html`）截图。这里有个容易踩的坑：如果页面布局用了 `min-height:100vh` 撑满视口（很多后台风格布局都这样），截图窗口开太高会在内容和页脚之间截出一大块空白，所以**每个页面要按内容实际高度单独试一个合适的 `--window-size` 高度**，而不是所有页面用同一个尺寸。具体细节见 `references/screenshot_capture_recipe.md`。
- 生成完用 `python -c "from docx import Document; ..."` 读一遍段落/表格/标题大纲，或者 `qlmanage -t` 出一张封面缩略图肉眼看一眼，确认没有明显错位——这一步不需要装 LibreOffice，比想象中轻量。

## 7. 打包提交前，把任务书的"提交要求"再读一遍

任务书通常会写清楚要交哪几样东西（源代码 / 说明书 / 演示视频）、交到哪个邮箱、什么截止时间——**打包前重新确认一遍这几点**，只打包任务书要求的东西，不要把老师给的 DEMO、原始数据表格、软件安装包这些素材也塞进提交包里。

打包时两个真实会翻车的地方：

- **macOS 自带的 `zip` 命令给中文文件名打包时，不会正确设置 Zip 的 UTF-8 文件名标记位**，导致 Windows 那边解压出来文件名是一串问号或乱码（这不是运气问题，是 Apple 那个 zip 版本的固定行为，试过设置 locale、试过 `-UN=UTF8` 参数都绕不过去）。**换成 Python 的 `zipfile` 模块手动打包**就没有这个问题——Python 3.7+ 的 `zipfile` 遇到非 ASCII 文件名会自动正确打上 UTF-8 标记位。`scripts/safe_zip.py` 封装了这个逻辑，传要打包的文件/文件夹列表和输出路径就行，打包完会自动校验每个非 ASCII 条目是不是都带上了标记位。
- **如果源代码文件夹名是中文，且需要部署到 Windows 上的 Apache（WampServer 这类环境），路径里的中文在某些系统编码设置下会导致 Apache 访问 404。** 稳妥起见把要放进 Web 服务器站点目录的那个源代码文件夹改成英文名（内部页面标题、页面里显示的中文系统名不用改，只改**文件夹名**这一层，因为所有页面间的链接都是相对文件名，不含目录路径，改文件夹名不会影响任何功能）。report 文档、zip 包本身的文件名可以留中文，这些是人在 Finder/资源管理器里打开，不经过 Web 服务器解析路径，没有这个风险。

## 部署兼容性自查（老师给老版 WampServer 时）

不要打包票说"肯定没问题"，但可以做几项具体检查给出有依据的判断：`grep` 一遍代码有没有 `??`、箭头函数等 PHP 7+ 语法；确认用没用 `mysqli_stmt_get_result()`（依赖 mysqlnd 驱动，官方 Windows 版 PHP 5.3+ 默认带，WampServer 用的就是官方编译版，一般没问题，但可以提醒用户"如果登录直接报 undefined function，去 WampServer 的 PHP 扩展菜单确认 mysqli 扩展开着"）；`conn.php` 里的账号密码要用 `localhost/root/空密码` 这种 WAMP 默认配置，除非用户另有说明。

用户在自己 Windows 上跑起来之后经常会贴报错截图回来让你远程排查——你没法登录他们的机器，只能靠"看图 + 问诊断结果"一步步定位，`references/wamp_troubleshooting.md` 整理了几个已经遇到过的典型故障链（连不上 MySQL、mysqli 函数未定义、php.ini 是空文件、SQLyog 脚本只执行了一半），按图索骥能省很多来回猜测的轮次。

## 形态B：上机操作考试

跟形态A完全不同的另一种任务形状：任务书本身是一张按大题小题给分的"考卷"（每题写着"完成并截图得X分"），没有 DEMO 网站可参考，只有几个孤立的小任务（建库建表、写连接文件、写一两个简单的表单+处理页），**最终交付物是把截图贴回这份 docx 试卷本身**，不需要另写说明书。

### 怎么做

- **代码你可以全部先写好、在本地隔离环境里测试通过**，跟形态A第4节一样起一个隔离 MySQL + PHP 内置服务器验证逻辑没问题，然后把代码交给用户，让他们直接复制到自己的 WampServer 里跑、截图，没必要每一步都等用户确认。
- **但凡任务书里要求"打开 XX 软件""修改配置文件里的某一项""用数据库工具建库"这种纯操作步骤，你做不了，也别假装能做**——如实告诉用户这几步需要他们自己在 Windows 上动手截图，你负责把每一步要点哪里、改什么写成清单（可以整理成一份独立的 markdown 操作步骤文档，比堆在聊天记录里方便他们对照执行）。
- **文件夹命名和文件位置严格按任务书原文的例子来**，任务书通常会给一个具体例子（比如"2400000001张三PHP动态网站开发上机补考"），不要按自己理解的格式（比如去掉某些字、加上"考生"之类的修饰词）自由发挥；学号/姓名等真实身份信息问用户要，用户不方便当场给的话就先用占位符把所有文件和文件夹结构搭好，等用户确认后再统一替换（一次替换到位，别遗漏 SQL 脚本里、文件夹名里的占位符）。
- **任务要求"以任意方式创建数据库/数据表"这类描述时，写一份 SQL 脚本让用户在 SQLyog/phpMyAdmin 里执行，比让他们从 GUI 里一步步点鼠标建表更快也更不容易出错**，脚本本身的执行过程截图就满足"以任意方式"的要求。
- **这类任务经常是"你写代码 → 用户在 Windows 上测试 → 报错截图发回来 → 你诊断 → 用户再试"的多轮来回**，把每一步遇到的环境问题当成正常节奏，不要指望一次性给出万能方案；`references/wamp_troubleshooting.md` 里整理了几类高频故障，遇到报错先去对一遍。
- **用户会在这个过程里不断更新那份 docx 试卷**（自己往里面贴截图），如果他把新版 docx 发给你要求"替换答题文件夹里的这份、重新打包"，直接照做——这类任务允许反复迭代打包，不用每次都重新问一遍"确定吗"，用 `scripts/safe_zip.py` 重新生成就行。
- **留意任务本身的业务逻辑陷阱**：比如"添加班长的数据"这种描述，容易被用户理解成"随便填点数据测试"，结果如果班长学号跟自己之前插入的记录学号重复（撞主键），会报错但用户搞不清为什么——提醒清楚"这一步要填的是另一个人的信息，不是你自己的"。
